# git.ge — build spec
 
This file is the brief for Claude Code. Read it fully before writing any code.
 
## What we're building
 
A static website at **git.ge** that lists open-source projects by Georgian
developers, with a monthly roundup and a path to becoming a community hub.
Georgian-language UI first, English secondary.
 
There is **no backend and no database**. GitHub is the storage layer: a
scheduled GitHub Action fetches data, commits JSON snapshots back to the repo,
regenerates static HTML, and deploys it.
 
## Stack — do not substitute
 
- **Fetcher:** C# / .NET 10 file-based app (`dotnet run fetch.cs`). Not Node,
  not Python, not a full csproj unless a single file genuinely can't work.
- **Site generation:** plain static HTML/CSS generated by a C# script in the
  same repo. No Next.js, no React, no SPA framework. Vanilla JS only where it
  is actually needed (filtering, sorting).
- **Storage:** JSON files committed to this repo under `data/`.
- **CI:** GitHub Actions, scheduled nightly.
- **Hosting:** Cloudflare Pages, custom domain git.ge. (Netlify is the
  fallback; keep the deploy step isolated to one workflow file so switching is
  a one-file change.)
## Data model
 
Design this first and show it to me before writing anything else.
 
A **project** record needs at minimum:
 
- `fullName` (owner/repo), `htmlUrl`, `description`, `descriptionKa` (optional
  manual Georgian description)
- `owner`, `ownerType` (user/org)
- `stars`, `forks`, `openIssues`
- `language` (primary), `topics`
- `pushedAt`, `createdAt`
- `category` (manual or inferred — see below)
- `source`: `"discovered"` | `"submitted"`
- `featured`: bool, `hidden`: bool (opt-out), `verified`: bool
A **developer** record: login, name, location as reported, profile URL,
`optedOut` bool, optional manual override of "is Georgian".
 
A **snapshot** is a compact daily record of `fullName -> stars` used to compute
trending. Keep these small — they are committed every day.
 
Decide the on-disk layout (one file per entity vs. one index file) and justify
it briefly. Optimise for: small diffs per commit, and a single JSON index the
browser can fetch for client-side filtering.
 
## Discovery rules
 
Two sources, merged:
 
1. **Auto-discovery via GitHub API.** Search users by location. "Georgia"
   alone overwhelmingly matches the US state — **never search that bare
   string**. Search city names and Georgian script instead: Tbilisi, თბილისი,
   Batumi, ბათუმი, Kutaisi, ქუთაისი, Rustavi, რუსთავი, Zugdidi, Gori,
   საქართველო, and `location:georgia` only when combined with a disambiguating
   term. Keep this list in a config file, not hardcoded in logic.
2. **Manual submissions.** A GitHub issue form (`.github/ISSUE_TEMPLATE/`) for
   submitting a project, plus a curated `data/manual/` file for entries added
   by PR. This catches devs who don't set a location and projects hosted
   outside GitHub.
**Quality bar** for auto-discovered repos (configurable, these are defaults):
not a fork, not archived, has a description, and (>= 3 stars OR pushed within
the last 12 months). Without a bar the list fills with homework repos.
 
**Opt-out is mandatory.** A developer or project can be excluded via a file in
the repo. Honour `hidden`/`optedOut` everywhere, including the JSON the site
ships. Document how to request removal on the site.
 
## Ranking rules
 
- **Default sort is trending**, not all-time stars: stars gained in the last 30
  days, computed by diffing today's snapshot against the closest snapshot ~30
  days old. Handle missing snapshots gracefully (new projects, gaps in history).
- All-time stars available as an explicit sort option.
- "New this month" and "Recently active" sections surface near the top.
- Category-first browsing (Web, Mobile, .NET, Data, DevOps, Libraries, Tools,
  Learning, Other) so no single project dominates the page.
- **The site maintainer's own projects are excluded from featured/spotlight
  picks.** They still appear in the normal listings and all-time sort. Put the
  maintainer's GitHub login in config and make this rule explicit in the code
  and visible on the site.
## GitHub API constraints — handle these in code, not at runtime
 
- The **search** API is rate-limited far more tightly than the core API
  (roughly 30 requests/minute authenticated) and returns **at most 1,000
  results per query**. Split user searches by city and by account-creation date
  ranges to stay under the cap; assume any single broad query is truncated.
- Core API is ~5,000 requests/hour authenticated.
- Use conditional requests / ETags where possible, and always read the
  `X-RateLimit-*` headers and back off rather than hammering.
- **Split the cadence:** full user discovery weekly, refresh of already-known
  repos nightly. Two workflows or one workflow with a mode flag.
- Auth with `GITHUB_TOKEN` in Actions; support a local `GH_TOKEN` env var for
  development.
- Scheduled workflows can fire late under GitHub load. That's fine — nothing
  here is time-critical. Never assume exact cron timing.
## Repo bloat
 
Daily full snapshots will bloat the repo over time. Store compact snapshots
(just `fullName` -> stars), and roll snapshots older than ~90 days into monthly
ones. Implement the pruning step in the same workflow.
 
## Site requirements
 
- **Georgian first.** UI strings in Georgian, with an English toggle. Keep all
  strings in a resource file, not inline in templates.
- **The main listing must work with JavaScript disabled.** Generate the default
  view as real HTML. JS only enhances (filter, sort, search).
- Page loads in under a second on a normal connection. No web fonts over 100KB
  total, no tracking scripts, no cookie banner because there are no cookies.
- Responsive; most local traffic will be mobile.
- Per-project cards showing: name, Georgian description if present, language,
  stars, trend delta, last activity, "help wanted" badge if the repo has open
  `good first issue` / `help wanted` issues.
- A `/help-wanted` page aggregating good-first-issues across all listed projects.
- Roundup posts as markdown files in `content/roundups/`, rendered to static
  pages, with an RSS feed.
- `robots.txt`, sitemap, and sensible OG tags so shared links look right.
## Design direction
 
Dense, fast, text-first. Closer to a well-made reference site than a startup
landing page: no hero section, no stock photography, no gradient blobs. Good
typography carries it. Must render Georgian script properly — pick and test a
font stack that handles Mkhedruli well, and check it on Windows, macOS and
Android defaults.
 
Dark mode via `prefers-color-scheme`.
 
## Build order — follow this sequence
 
1. Data model + on-disk layout. Show me before proceeding.
2. `fetch.cs` — discovery and refresh. Run it for real against the GitHub API
   and commit a sample of actual data.
3. Trending computation over committed snapshots (write a couple of fixture
   snapshots to test the 30-day diff logic).
4. Static site generator, styled against the **real** data from step 2.
5. Submission issue forms + the script that turns accepted submissions into
   data entries.
6. GitHub Actions workflows — last, once the scripts run clean locally.
7. Cloudflare Pages deploy + custom domain notes in the README.
## Ground rules
 
- Don't invent data. If the API doesn't give a field, leave it null and show
  nothing rather than guessing.
- Ask me before adding any dependency beyond the .NET BCL and a JSON library.
- Small commits with clear messages; I want to be able to read the history.
- Write a short README explaining how to run the fetcher locally and how the
  data flows. That README is for contributors, so it should be honest about
  what's manual.
- No analytics, no third-party embeds, no external CDN requests from the
  rendered site.
## Out of scope for v1
 
Logins, self-service paid job posting, comments, voting, email newsletter
infrastructure. If any of those become necessary later they'll go through
Cloudflare Workers or an external service — don't build a backend for them now.
